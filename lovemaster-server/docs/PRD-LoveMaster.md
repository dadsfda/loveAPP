# LoveMaster 产品需求文档 PRD

**文档版本**：v1.6-current
**更新时间**：2026-04-29
**产品阶段**：H5 MVP 已上线验证，微信小程序上线前准备中
**产品定位**：情侣关系的日常经营增效工具
**后端项目**：`lovemaster-server`

## 1. 背景与问题

稳定情侣关系中，很多矛盾并不来自重大价值观冲突，而来自高频、低烈度、重复发生的日常摩擦。例如忘记纪念日、临时不知道约会做什么、家务分工不清、不了解对方偏好、争吵时表达方式升级。这些问题本身不复杂，但会持续消耗关系质量。

LoveMaster 的目标不是替情侣判断关系，也不是制造新的任务负担，而是提供一个轻量、低打扰、可共同维护的关系经营工具，帮助情侣减少日常琐碎摩擦，增加仪式感和共同回忆。

## 2. 产品目标

### 2.1 核心目标

1. 降低情侣日常经营成本，避免“忘记、没准备、不知道怎么说”造成的摩擦。
2. 增强双方共同参与感，通过纪念日、偏好、约会灵感和回忆记录形成正向循环。
3. 在出现矛盾时提供非评判性的沟通参考，帮助用户降温、表达和复盘。

### 2.2 非目标

1. 不判断情侣关系对错。
2. 不替用户做分手、原谅、妥协等重大决定。
3. 不把个人倾诉内容默认共享给另一方。
4. 不做伴侣监控、定位追踪、消息监控等控制型功能。
5. MVP 阶段不做复杂社交、内容社区、商城和商业化系统。

## 3. 产品原则

### 3.1 不越界

所有建议都以“仅供参考”“可协商调整”为前提。系统提供思路、模板和灵感，不输出绝对判断。

### 3.2 隐私优先

产品必须区分个人模式和双人模式：

- 个人模式：仅本人可见，例如个人倾诉、个人提醒、惊喜计划。
- 双人模式：双方均可见，例如共同纪念日、共同回忆、共同偏好清单。

共同记录需要明确可见性，不能因为双方已配对就默认共享所有内容。

### 3.3 正向导向

所有文案和功能设计应强调尊重、平等、协商和表达。避免鼓励单方忍让、情绪操控、道德绑架或控制行为。

### 3.4 低打扰

LoveMaster 不应成为“多一个需要维护的系统”。默认交互应轻量，提醒克制，记录入口简单。

## 4. 目标用户

### 4.1 核心用户

稳定交往中的情侣，已经有共同生活、约会或长期经营关系的需求，希望通过工具减少日常摩擦。

### 4.2 次级用户

1. 异地情侣：需要记录共同目标、纪念日和远程互动灵感。
2. 同居情侣：更关注家务分工、偏好记录、生活习惯和矛盾预防。
3. 新建立关系的情侣：更关注仪式感、约会灵感和了解对方。

### 4.3 典型用户画像

**用户 A：容易忘事的一方**

- 痛点：经常忘记纪念日、生日、重要约定。
- 期待：提前提醒，并给出低成本准备建议。

**用户 B：重视仪式感的一方**

- 痛点：希望关系被认真对待，但不想每次都由自己推动。
- 期待：共同维护纪念日和回忆，看到对方参与。

**用户 C：不擅表达的一方**

- 痛点：争吵时容易说重话，事后不知道怎么修复。
- 期待：有表达模板和复盘引导，但不被说教。

## 7. 核心业务流程

### 7.1 注册登录流程

1. 用户通过用户名和密码注册。
2. 系统创建用户并生成唯一配对邀请码。
3. 用户登录后获得 access token 和 refresh token。
4. refresh token 写入 Redis，用于刷新和登出控制。

### 7.2 配对流程

1. 用户 A 注册后获得 `pairCode`。
2. 用户 A 将邀请码发给用户 B。
3. 用户 B 输入邀请码发起配对。
4. 系统校验：
   - 邀请码存在。
   - 邀请码不是自己的。
   - 双方当前均未处于有效配对关系。
5. 系统建立情侣关系，并更新双方用户的 `partnerId` 和 `pairedAt`。
6. 双方可查看当前配对状态。

### 7.3 纪念日流程

1. 已登录用户创建纪念日。
2. 用户选择可见性：
   - 仅自己可见。
   - 双方可见。
3. 如果选择双方可见，用户必须处于有效配对关系。
4. 用户设置提醒提前天数，例如当天、提前 1 天、提前 3 天、提前 7 天。
5. 用户可查询所有自己可见的纪念日。
6. 系统可查询未来指定天数内需要提醒的纪念日。

## 8. 详细功能需求

### 8.1 账号认证

#### 8.1.1 注册

用户可以通过用户名和密码注册账号。

**输入字段**

- 用户名：必填，3 到 50 个字符。
- 密码：必填，6 到 100 个字符。
- 昵称：选填，默认等于用户名。
- 手机号：选填，唯一。
- 邮箱：选填，唯一。

**业务规则**

1. 用户名不能重复。
2. 手机号不为空时不能重复。
3. 邮箱不为空时不能重复。
4. 密码必须加密存储。
5. 注册成功后生成 8 位配对邀请码。

**验收标准**

1. 注册成功返回用户基础信息和配对邀请码。
2. 返回内容不包含密码哈希。
3. 重复用户名返回业务错误。

#### 8.1.2 登录

用户可以通过用户名和密码登录。

**业务规则**

1. 用户不存在时返回用户不存在错误。
2. 密码错误时返回密码错误。
3. 用户被禁用时禁止登录。
4. 登录成功返回 access token 和 refresh token。
5. refresh token 写入 Redis，过期时间为 7 天。

**验收标准**

1. 登录成功返回 `tokenType=Bearer`。
2. access token 可通过 JWT 校验。
3. Redis 中存在对应用户的 refresh token。

### 8.2 情侣配对

#### 8.2.1 查看我的配对状态

用户可以查看自己是否已配对，以及伴侣基础信息。

**返回字段**

- 是否已配对。
- 当前用户 ID。
- 伴侣用户 ID。
- 伴侣昵称。
- 配对时间。
- 当前用户的邀请码。

**验收标准**

1. 未配对用户返回 `paired=false`。
2. 已配对用户返回伴侣基础信息。
3. 不返回伴侣手机号、邮箱等敏感字段。

#### 8.2.2 输入邀请码配对

用户输入另一方的邀请码完成配对。

**业务规则**

1. 不能使用自己的邀请码。
2. 邀请码不存在时返回错误。
3. 当前用户已配对时不能再次配对。
4. 被邀请用户已配对时不能再次配对。
5. 配对成功后双方互为伴侣。

**验收标准**

1. 配对成功后双方 `partnerId` 互相指向。
2. 双方 `pairedAt` 一致或接近同一时间。
3. 再次使用同一邀请码配对失败。

#### 8.2.3 解除配对

用户可以解除当前配对关系。

**业务规则**

1. 未配对用户调用时返回业务错误或幂等成功，MVP 建议返回业务错误。
2. 解除后双方 `partnerId` 清空。
3. 双方共同可见数据保留，但后续访问策略需要明确。

**MVP 访问策略**

解除配对后，历史双方共同数据暂时不可被任何一方继续修改；读取权限保留给创建者。更复杂的共同数据归属策略后续版本再做。

### 8.3 纪念日管理

#### 8.3.1 创建纪念日

用户可以创建纪念日或重要日期。

**字段**

- 标题：必填，1 到 50 个字符。
- 日期：必填，格式为日期。
- 类型：必填，支持 `LOVE_ANNIVERSARY`、`BIRTHDAY`、`CUSTOM`。
- 可见性：必填，支持 `PRIVATE`、`COUPLE`。
- 提醒提前天数：可选集合，支持 0、1、3、7。
- 惊喜模式：布尔值，默认 false。
- 备注：选填，最多 500 字。

**业务规则**

1. 个人可见纪念日不需要配对。
2. 双方可见纪念日必须已配对。
3. 惊喜模式只允许个人可见，避免“惊喜”被自动共享。
4. 标题和备注需要做长度校验。
5. 删除采用逻辑删除。

**验收标准**

1. 创建成功返回纪念日详情。
2. 未配对用户创建双方可见纪念日失败。
3. 惊喜模式和双方可见同时出现时失败。

#### 8.3.2 查询纪念日列表

用户可以查询自己可见的纪念日。

**可见范围**

1. 自己创建的个人纪念日。
2. 自己创建或伴侣创建的双方可见纪念日。

**筛选条件**

- 类型。
- 可见性。
- 起止日期。

**排序**

默认按下一个到来日期升序排序。

**验收标准**

1. 未配对用户只能看到个人纪念日。
2. 已配对用户可以看到双方可见纪念日。
3. 看不到其他情侣或其他用户的数据。

#### 8.3.3 编辑纪念日

用户可以编辑自己有权限管理的纪念日。

**业务规则**

1. 创建者可以编辑纪念日。
2. MVP 阶段，伴侣可以查看双方可见纪念日，但不能编辑对方创建的纪念日。
3. 编辑时仍需满足创建时的可见性和惊喜模式规则。

**验收标准**

1. 创建者编辑成功。
2. 非创建者编辑失败。
3. 非可见用户访问失败。

#### 8.3.4 删除纪念日

用户可以删除自己创建的纪念日。

**业务规则**

1. 删除采用逻辑删除。
2. 非创建者不能删除。

**验收标准**

1. 删除后列表不再返回该记录。
2. 数据库保留删除标记。

#### 8.3.5 查询提醒

系统支持查询未来 N 天内需要提醒的纪念日，为后续推送任务做准备。

**MVP 范围**

MVP 只提供查询接口或服务方法，不实际接入短信、邮件、App Push。

**验收标准**

1. 能查询未来 7 天内即将到来的纪念日。
2. 只返回当前用户可见且命中提醒配置的记录。

### 8.4 喜好清单

喜好清单用于记录双方偏好、禁忌和灵感线索，为后续约会推荐和纪念日建议提供基础数据。

**字段**

- 分类：饮食禁忌、喜欢的食物、兴趣爱好、礼物偏好、生活雷区、自定义。
- 内容：必填。
- 可见性：个人或双方。
- 关联对象：记录的是自己还是伴侣。
- 标签：可选，用于约会灵感推荐匹配。
- 备注：可选，用于补充偏好的来源或上下文。

**MVP v1.2 规则**

1. 用户可以记录自己的偏好。
2. 用户可以记录“我观察到的伴侣偏好”，但应明确这是自己的记录，不代表伴侣确认。
3. 双方可见偏好可以被伴侣看到。
4. 个人可见偏好仅创建者可见。
5. 双方可见偏好必须处于有效配对关系。
6. MVP 阶段仅创建者可编辑或删除偏好。

**验收标准**

1. 用户可以创建、查询、编辑、删除个人偏好。
2. 已配对用户可以创建双方可见偏好。
3. 未配对用户创建双方可见偏好失败。
4. 伴侣可以查看双方可见偏好，但不能编辑或删除对方创建的偏好。
5. 非关系内用户无法查看偏好。

### 8.5 约会灵感

约会灵感用于根据预算、时间、场景和兴趣给出低成本可执行建议。

**输入条件**

- 预算：免费、50 元内、100 元内、300 元内、不限。
- 时间：1 小时、2 小时、半天、一天。
- 场景：室内、室外、雨天、居家、异地。
- 兴趣标签：电影、美食、散步、手作、运动、拍照、学习。

**MVP v1.2 推荐策略**

优先使用内置模板和规则匹配，不依赖大模型。

**输出内容**

- 标题。
- 适合场景。
- 预计预算。
- 预计耗时。
- 执行步骤。
- 小提示。

**内置模板要求**

1. MVP v1.2 至少内置 20 条约会灵感模板。
2. 每条模板至少包含标题、预算档位、耗时档位、场景、兴趣标签、步骤和提示。
3. 模板可以通过数据库初始化 SQL 写入，后续再做运营后台。

**推荐规则**

1. 用户传入预算、时间、场景、兴趣标签时，优先匹配全部条件。
2. 如果完全匹配结果不足，允许放宽兴趣标签匹配。
3. 如果用户已维护喜好清单，推荐接口可以优先匹配双方可见兴趣或创建者记录的偏好标签。
4. MVP 阶段推荐逻辑必须可解释，不引入黑盒排序。

**验收标准**

1. 用户可以按预算、时间、场景和兴趣标签查询约会灵感。
2. 推荐接口返回结构化约会方案。
3. 推荐结果不依赖 AI 服务。
4. 未登录用户不能访问推荐接口。

### 8.6 回忆收藏夹

回忆收藏夹用于记录双方共同事件和重要瞬间。

**MVP v1.3 范围**

1. 支持文字记录。
2. 支持图片上传，并在回忆中保存图片 URL。
3. 支持日期和地点文本。
4. 支持个人可见和双方可见。
5. 支持按日期、标签、可见性筛选的时间线查询。

**MVP v1.3 规则**

1. 上传接口需要登录。
2. 图片静态访问路径 `/uploads/**` 可匿名访问。
3. MVP 阶段只支持单图，后续再扩展多图、缩略图、删除旧图和对象存储。
4. 回忆的编辑和删除仅允许创建者操作。
5. 双方可见回忆要求用户处于有效配对关系。
6. 伴侣只能查看双方可见回忆，不能编辑或删除。

**验收标准**

1. 用户可以上传 JPEG、PNG、WebP、GIF 图片，并获得 URL。
2. 用户可以创建带图片 URL 的个人回忆。
3. 配对用户可以创建双方可见回忆。
4. 未配对用户创建双方可见回忆失败。
5. 伴侣可以查看双方可见回忆，不能查看个人可见回忆。
6. OpenAPI 文档包含回忆和图片上传接口。

### 8.7 AI 沟通建议

AI 沟通建议用于在用户描述矛盾或表达困难时，提供非指责式、可协商的表达参考。该能力不保存用户输入，MVP v1.4 先做一次性建议接口。

**输入字段**

- 场景描述：必填，例如晚回消息、家务分工、陪伴不足、消费观差异。
- 我的感受：选填，例如委屈、生气、失落、担心。
- 对方可能的感受：选填，用于帮助表达更平衡。
- 沟通目标：选填，例如想表达需求、想降温、想道歉、想约定下次做法。

**输出原则**

1. 使用“我感受”表达。
2. 避免“你总是”“你从来不”等绝对化表达。
3. 给出可协商请求。
4. 明确建议仅供参考。
5. 不判断谁对谁错。
6. 不输出控制、试探、报复或道德绑架式建议。
7. 不做医疗、法律、心理诊断。

**返回字段**

- `advice`：沟通建议说明。
- `messageTemplate`：可直接参考的表达模板。
- `riskLevel`：风险等级，枚举值为 `low`、`medium`、`high`。
- `reminder`：固定安全提醒。

**MVP v1.4 规则**

1. 需要登录后调用。
2. API Key、模型、base URL、超时时间通过配置管理。
3. 未启用 AI 或未配置 API Key 时返回明确业务错误。
4. 外部 AI API 超时或失败时返回明确业务错误，不暴露底层密钥、请求头或完整异常堆栈。
5. 测试环境默认使用 mock 客户端，不真实调用外部 API。
6. API Key 使用环境变量 `DASHSCOPE_API_KEY`，禁止写入代码、配置文件、PRD、handoff 或测试夹具。
7. 默认 base URL 使用 `https://dashscope.aliyuncs.com/compatible-mode/v1`。
8. 默认 HTTP endpoint 使用 `POST /chat/completions`。

**MVP v1.5 结构化输出规则**

1. 提示词要求模型只返回合法 JSON 对象，不返回 Markdown 代码块或额外解释。
2. 服务端优先解析 JSON 字段 `advice`、`messageTemplate`、`riskLevel`。
3. `riskLevel` 只允许 `low`、`medium`、`high`，其他值统一降级为 `low`。
4. `reminder` 由服务端固定生成，不信任外部模型返回的免责声明。
5. 如果模型返回非 JSON 文本，服务端保留旧版文本拆分能力，并返回默认 `riskLevel=low`。
6. 如果 JSON 缺少 `advice` 或 `messageTemplate`，服务端使用保守兜底文案补齐。

## 9. AI 能力边界

### 9.1 MVP v1.1-v1.3 阶段

MVP v1.1-v1.3 不接入 AI。所有功能先通过确定性业务逻辑完成。

### 9.2 MVP v1.4 AI 能力

MVP v1.4 可以接入通义千问 API，但只做一次性沟通建议，不做 Agent 长对话：

1. 根据争执场景提供沟通表达建议。
2. 根据用户感受生成“我感到...因为...我希望...”表达模板。
3. 在输出中提示用户结合双方真实情况协商。
4. 对高风险内容给出安全提醒，而不是继续生成关系策略。

### 9.3 后续 AI 能力

后续可在以下场景接入更完整的 Agent：

1. 根据纪念日类型推荐庆祝方案。
2. 根据偏好清单推荐约会灵感。
3. 根据双方复盘内容提炼共识点。
4. 多轮情绪降温和复盘引导。

### 9.4 AI 安全边界

AI 输出必须遵守：

1. 不判断谁对谁错。
2. 不建议用户忍受暴力、控制或羞辱。
3. 不鼓励监控、试探、报复。
4. 不做医疗、法律、心理诊断。
5. 遇到自伤、暴力、威胁等高风险内容时，优先给出安全建议和求助渠道。
6. 输出中标注“建议仅供参考，具体做法需要结合你们双方情况协商”。

## 10. 权限与隐私需求

### 10.1 数据可见性

系统数据至少支持两种可见性：

- `PRIVATE`：仅创建者可见。
- `COUPLE`：创建者和当前有效配对伴侣可见。

4. 伴侣在 MVP 阶段默认只有查看权限。
5. 管理后台不在 MVP 范围内。

### 10.3 敏感信息

伴侣之间默认不展示手机号、邮箱、登录信息、token 信息。

### 10.4 删除策略

业务数据采用逻辑删除，便于审计和误删恢复。用户注销和彻底删除属于后续合规专项。

## 13. 非功能需求

### 13.1 性能

MVP 阶段接口响应目标：

- 普通查询接口 P95 小于 300ms。
- 创建、编辑、删除接口 P95 小于 500ms。
- 登录接口 P95 小于 800ms。

### 13.2 安全

1. 所有非认证接口必须 JWT 鉴权。
2. 密码使用 BCrypt 存储。
3. token 过期时间遵循当前配置。
4. refresh token 存 Redis，登出时删除。
5. 所有涉及用户 ID 的查询必须做权限校验。

### 13.3 可测试性

1. Service 层覆盖核心业务规则。
2. Controller 层覆盖参数校验和响应格式。
3. 测试环境使用 H2，Redis 使用 mock 或测试容器。
4. 新增模块必须有成功路径、权限失败、参数失败测试。
5. OpenAPI 文档访问需要有自动化测试兜底。

### 13.4 可运维性

1. 本地开发使用 Docker Compose 启动 MySQL 和 Redis。
2. 数据库 schema 统一维护在 `src/main/resources/db/schema.sql`。
3. 日志记录业务异常和非预期异常。
4. 不在日志中打印密码、token、隐私内容。
5. Apifox 通过 `/v3/api-docs` 导入接口，避免手工维护接口集合。

## 17. 主要风险与应对

### 17.1 隐私边界不清

风险：用户以为个人记录被伴侣看到，造成信任问题。

应对：所有创建入口必须明确可见性；个人模式默认仅自己可见。

### 17.2 AI 建议越界

风险：AI 输出关系判断、过度劝和或错误建议。

应对：v1.4 只接入边界明确的一次性沟通建议；v1.5 增强结构化输出、固定免责声明、异常降级和测试隔离，再考虑更复杂的 Agent 能力。

### 17.3 功能过重导致低频

风险：产品像任务管理工具，用户维护成本高。

应对：MVP 只做配对和纪念日，表单字段克制，提醒可选。

### 17.4 共同数据归属复杂

风险：解除配对后共同数据归属和权限产生争议。

应对：MVP 明确规则为“创建者可管理，伴侣只读；解除后共同数据不再共同编辑”。

## 18. 开放问题

1. 微信小程序首版是复用 H5 业务结构重写原生小程序，还是先用 WebView/云托管方式过渡。
2. 线上图片是否立即迁移到 CloudBase Storage，并同步设计图片删除、压缩、缩略图和多图能力。
3. 是否允许用户更换或刷新邀请码。
4. 解除配对是否需要二次确认、冷静期或二次输入。
5. 纪念日是否需要农历支持。
6. 未来提醒通过站内提醒、微信订阅消息、邮件、短信还是 App Push 实现。
7. 喜好清单是否允许伴侣“确认”或“纠正”对方观察到的偏好。
8. 约会灵感模板是否需要支持城市、天气、营业时间等外部数据。
9. 生产 AI 是否启用，启用后是否需要记录 AI 调用日志和 token 用量；日志不得记录用户正文与密钥。
10. CloudBase MySQL 运维账号、测试数据清理和备份策略如何规范化。

## 19. 下一步建议

1. 优先把回忆图片从 CloudRun 本地目录迁移到 CloudBase Storage，解决线上图片持久化风险。
2. 梳理微信小程序上线形态：项目结构、AppID、页面路由、底部 Tab、登录方式、上传能力和云开发权限。
3. 补齐喜好、纪念日、回忆的编辑/删除体验，保持“先展示，点加号或编辑按钮再进入表单”的交互原则。
4. 增加线上环境健康检查和数据运维说明，包括 CloudRun、CloudBase MySQL、静态托管和构建部署命令。
5. 生产 AI 继续保持一次性建议，不做长对话 Agent、不读取历史隐私数据、不持久化情绪正文。
6. 小程序上线前完成真机走查：注册、登录、配对、首页、喜好、灵感、回忆、我的页和退出登录。
